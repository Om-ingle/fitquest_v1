# Phase 4B.3 — ML Target Design (XGBoost Experiment #1)

> ⚠ **Everything here is computed from SYNTHETIC data** generated by
> `generator.py`. This document defines a target and validates that the
> *data path* is well-posed. It does **not** claim the target is predictable
> for real FitQuest users, and it establishes no real-world predictive
> performance. Real FitQuest telemetry will eventually replace/augment the
> synthetic dataset.

Status: **design only.** No model is trained in this phase; no target column
is added to `synthetic_fitness_features.csv` (features stay purely
historical). The executable definition lives in `target.py`; the analysis is
reproducible via `python tools/synthetic_fitness/target.py`.

---

## 1. What should the first XGBoost model predict?

**Near-term user disengagement**: whether a user is about to go quiet.
Concretely, from the 21 leakage-safe features as of the end of day D, the
model predicts whether the user will be meaningfully inactive over the next
three days.

This is the first experiment because it is (a) well-distributed in the
current dataset (§"Label distribution" below), (b) production-relevant
(FitQuest's whole loop dies when a player goes quiet — an early-warning
signal drives timely, gentle nudges), and (c) independent of the existing
rules engine (§5).

## 2. Mathematical / operational definition

Let `bar = 1000` steps (the game's existing activity bar, `STREAK_MIN_STEPS`
— also the streak/capture threshold, so "inactive" has one consistent
meaning across the product). For a user u on day D:

```
inactive(u, d)        := 1[steps(u, d) < 1000]

inactive_next_3d(u,D) := 1[ Σ_{k=1..3} inactive(u, D+k)  >=  2 ]
```

**Operational reading:** "at least 2 of the next 3 days are below the
activity bar." The 2-of-3 rule distinguishes *disengagement* from a single
planned rest day: an athlete who takes one recovery day out of three stays
label 0; a user drifting into a gap is labeled 1.

Binary classification. Implemented in `target.py`
(`TARGET_NAME = "inactive_next_3d"`, `HORIZON_DAYS = 3`,
`INACTIVE_DAYS_REQUIRED = 2`, `INACTIVE_STEPS_MAX = 999`).

## 3. Prediction horizon

**3 days (D+1..D+3), inclusive of all three days.** Short enough to be
actionable (the coach can still intervene), long enough to smooth out single
rest days, and fully supported by the data: every user has 180 days of
history, so 5,310 of 5,400 rows carry a complete label.

## 4. Why this target is useful for FitQuest recommendations

- The core loop (hexes, streaks, quests, leaderboards) collapses the moment
  a player stops opening the app. Predicting the *onset* of a quiet spell is
  the highest-leverage moment for a recommendation: nudge before the streak
  breaks, before territory sits undefended, before the LAPSED state the
  rules engine can only react to *after the fact*.
- It is a *leading* signal: the rules engine fires RECOVERY/RE-ENGAGE rules
  on already-elapsed inactivity (`days since capture > 2`). A model that
  predicts inactivity 1–3 days ahead moves the system from reactive to
  anticipatory.
- It is well-defined for every user every day (no territory ownership
  required), unlike territory-loss targets which are undefined for users
  holding nothing.

## 5. Why NOT label with the rules engine's recommendation

Using `STARTER / RECOVERY / DEFENSE / PROGRESS / MAINTAIN` as ground truth
would be **circular**:

1. The rules engine's output is a *deterministic function of the same
   features* we would feed the model (recent activity, captures, territory,
   streaks). The "best achievable model" is then exactly the rules — the
   experiment can only measure how well XGBoost approximates a known
   function of its own inputs.
2. It teaches the model the rules engine's *opinions*, including its bugs
   and its thresholds (e.g. the 2-day capture window), not anything new
   about users.
3. Any reported accuracy would be misleading: "95% agreement with the rules"
   is not "95% good recommendations" — there is no independent notion of
   correctness in the label.
4. It forecloses the actual reason to add ML: discovering signal the rules
   don't encode.

A future-behavior target (this design) breaks the circle: the label comes
from *what the user actually did next*, which the rules engine does not
determine.

## 6. Which future rows construct the target (and no leakage into features)

- The label for (u, D) reads **exactly days D+1, D+2, D+3 of user u** — no
  other days, no other users. Enforced by construction in
  `build_labels()` and proven by tests (`test_label_uses_exactly_the_next_three_days`:
  mutating D+4 or later cannot change D's label; mutating D+1..D+3 does).
- **Feature/label separation is structural:** features (`features.py`) are a
  pure function of days ≤ D; labels (`target.py`) are a pure function of
  days D+1..D+3. The target is not a column in
  `synthetic_fitness_features.csv` (`test_target_is_not_part_of_the_feature_matrix`),
  so it is impossible for a downstream join to leak it into the matrix.
- The Phase 4B.2 leakage tests already prove the feature side (perturbing
  any day > D leaves day D's features byte-identical; tampering with another
  user's history leaves a user's features identical).

## 7. Rows near the end of each user's history

The last `HORIZON_DAYS` (= 3) days of each user's history have no complete
future window. They are **excluded from the labeled experiment set — label
`None`, never imputed, never forward-filled**. That removes 90 rows
(30 users × 3 days) from the 5,400 feature rows, leaving **5,310 labeled
samples**. The corresponding feature rows still exist in the features CSV
(they remain useful for inference-only use later); they are simply dropped
at the join.

## 8. Time-aware train/validation/test split

**By calendar date, across all users** (production-realistic: train on the
past, evaluate on the future). Random row-level splits would leak via
within-user autocorrelation (day D and D+1 of the same user are nearly the
same sample). User-level splits would avoid that too but waste the
"generalize across time" question that matters for deployment, and with
only 30 synthetic users they'd starve the test set.

| Split  | Calendar dates              | History index | Labeled rows | Positives | Prevalence |
| ------ | --------------------------- | ------------- | ------------ | --------- | ---------- |
| train  | ≤ 2025-05-17                | 0..136        | 4,110        | 1,870     | 45.5%      |
| embargo| 2025-05-18 .. 2025-05-20    | 137..139      | 90 (unused)  | 41        | 45.6%      |
| val    | 2025-05-21 .. 2025-06-09    | 140..159      | 600          | 267       | 44.5%      |
| test   | 2025-06-10 .. 2025-06-26    | 160..176      | 510          | 239       | 46.9%      |

The **3-day embargo** exists so that no training row's target window
(D+1..D+3) reaches into the validation period — without it, a training
sample at day 139 would "know" outcomes from days 140–142, which are
validation days (`test_every_training_targets_window_stops_before_validation`).
Calendar dates (rather than per-user indices) are used so uneven real-world
histories slot into the same policy unchanged.

Known caveat (documented, not hidden): the LAPSED profile's forced inactive
tail is a fixed ~40% window at the end of the history, so in the *test*
period LAPSED users are almost all label-1. This makes the test set slightly
easier on that profile. The overall prevalence stays stable (45.5 → 44.5 →
46.9%), and mid-activity profiles (CASUAL/RETURNING, ~50%) carry the
discriminative load.

## 9. Baselines

1. **Majority class** — always predict the training prevalence side (here:
   predict "inactive_next_3d = 1" would get 45.5% on train; report both
   class-majority accuracy and the prevalence itself).
2. **Persistence heuristic** — predict 1 iff the user is *already* inactive
   today (`active_today == 0`, i.e. steps_today < 1000). This is the strong,
   honest null: it asks whether the 21 features add anything beyond "they
   were quiet today". (A model that only wins against majority-class but
   ties persistence has learned nothing useful.)
3. Optional third reference: `days_since_active >= 1` (inactivity-streak
   heuristic), to show marginal value over a slightly richer rule.

A trained model must beat baseline #2 on the primary metric to count as
progress.

## 10. Evaluation metrics

- **ROC-AUC (primary):** threshold-free, interpretable under the ~45% base
  rate, and directly comparable against the persistence baseline.
- **PR-AUC (secondary):** the day-to-day operational question is precision
  at usable recall; PR-AUC is sensitive to that.
- **Accuracy + F1 at a validation-tuned threshold** (threshold chosen on
  val, frozen, applied once to test).
- **Brier score / calibration curve** (reported, secondary): a coach that
  says "70% likely to go quiet" should mean it.
- Always reported **with the split's positive prevalence** so numbers can't
  be read without their base rate. No accuracy claims without the baselines
  next to them.

## 11. What success / failure would mean

- **Success** = test ROC-AUC meaningfully above the persistence baseline
  (working target: ≥ +0.05) *and* above majority-class, with val/test
  metrics agreeing within noise. Meaning: the 21 features contain signal
  about *near-future* disengagement beyond current-state persistence — in
  the synthetic world. That justifies building the same target on real
  telemetry.
- **Failure** = at or below the persistence baseline. Meaning: within this
  (synthetic) data-generating process, current state already determines the
  label; the richer history features add nothing. It would **not** mean the
  product idea is wrong — only that this feature set / horizon / target
  carries no additional extractable signal, and Phase 4B.4 should change the
  target or features rather than ship a model.
- **Either way, no claim transfers to real users** (§12).

## 12. What this synthetic experiment can and cannot demonstrate

**Can:** that the end-to-end ML path is correct and leakage-free (features,
labels, splits, metrics); that the target is learnable *in principle* from
these features; how the pipeline behaves under class imbalance and
distribution shift; reproducible mechanics for the real experiment.

**Cannot:** real-user predictive performance (the profiles are a cartoon, by
design); real feature importances (e.g. `streak` matters here partly because
the generator builds streaks into the process); real calibration; real
base rates (nothing like 45% disengagement-per-3-days should be quoted
about FitQuest users); anything about the rules engine's quality.

The synthetic generator's own simplifications (uniform step draws, fixed
activity probabilities per profile, deterministic gaps) mean the label is
*easier* here than reality is likely to be. Treat any headline AUC as an
upper bound on pipeline sanity, not a forecast.

## 13. Consuming real FitQuest telemetry later

The path is already shaped for it:

1. Real daily aggregates land in Supabase with the same 12-column semantics
   (`user_id, day, steps, active_minutes, hexes_owned, hexes_captured,
   hexes_lost, defense_steps, streak, goal_steps, goal_completed,
   data_source='real'`) — sourced from run-sync writes and hex-ownership
   events, joined into one row per (user, day).
2. `features.py` and `target.py` are pure functions of those rows: no
   synthetic-specific logic beyond `data_source` labeling and the
   `syn_*` id convention (which `profile_from_user_id` already passes
   through harmlessly). Point `--input` at the real export; the same
   feature matrix, label, and calendar-date split policy apply.
3. Split boundaries become *real* dates chosen at experiment time; the
   embargo logic and tail-row exclusion carry over verbatim.
4. Mixed provenance is filtered by `data_source` — train/evaluate on real
   rows, keep synthetic rows for smoke tests only, and never pool them into
   one reported metric.

## Appendix: candidate targets examined and rejected (measured on the real
5,400-row dataset)

| Candidate | Overall + | Why rejected |
| --- | --- | --- |
| **inactive_next_3d (chosen)** | **45.5%** | — stable across splits (45.5/44.5/46.9%), both classes everywhere, meaningful profile spread |
| inactive_any_next_3d | 66.0% | "any" fires on a single rest day — weak disengagement semantics; INACTIVE/HIGHLY degenerate (100%/8%) |
| goal_met_any_next_3d | 56.2% | degenerate at the extremes (HIGHLY_ACTIVE 100%, INACTIVE 0%) — label ≈ profile identity; also near-duplicate of the activity target |
| goal_missed_all_next_3d | 43.8% | mirror of the above; 0%/100% extremes |
| territory_loss_next_3d | 10.0% | imbalanced; undefined/zero for users with no territory (INACTIVE 0%) |
| capture_next_3d | 15.6% | imbalanced and split-unstable (val drops to 8%) |
