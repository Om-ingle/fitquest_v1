# Backend Architecture & Schema (FastAPI + Supabase)

This document outlines the core architecture, database schema, and data contracts for the FitQuest backend API. The backend operates on **FastAPI**, **SQLModel**, and **Supabase (PostgreSQL)**.

## 🏗 Modular Domain-Driven Architecture

The backend is organized by strictly isolated feature modules to ensure zero-collateral breakage and infinite scalability.

### Project Structure

```text
apps/api/
├── .env                    # Environment variables (DATABASE_URL etc.) — never committed
├── requirements.txt        # Python dependencies (fastapi, sqlmodel, psycopg2, alembic)
├── requirements-dev.txt    # Test dependencies (pytest, httpx)
├── alembic.ini             # Database migration configuration
├── alembic/                # Alembic migrations (schema is reproducible from code)
│   ├── env.py
│   └── versions/
├── tests/                  # API and config tests
└── app/
    ├── main.py             # FastAPI application initialization
    ├── core/               # App-wide settings and engine config
    │   ├── config.py       # Pydantic BaseSettings (reads DATABASE_URL from env/.env)
    │   ├── database.py     # SQLAlchemy sync engine → Supabase PostgreSQL
    │   └── security.py     # Auth helper utilities (unused until auth phase)
    │
    ├── api/                # Global API logic
    │   ├── dependencies.py # get_db, get_current_user (dev-user stub — auth deferred)
    │   └── router.py       # Main router tying all modules together
    │
    └── modules/            # The Brains: Domain-Driven Modules
        ├── users/          # Profiles, Streaks, Friendships
        ├── map/            # Geospatial Viewports and King of the Hill (H3)
        ├── runs/           # End-of-Run Sync Engine
        └── quests/         # Daily/Global Challenges
```

### Module Separation of Concerns Rule
Inside *every* module, this strict rule applies:
* `router.py`: ONLY handles HTTP request parsing, calling dependencies, and returning response models.
* `service.py`: ONLY handles business logic, heavy math, and pure Python interactions with the database engine.
* `models.py`: ONLY defines the SQLModel database tables (PostgreSQL tables).
* `schemas.py`: ONLY defines the Pydantic shapes (DTOs) for incoming payloads and outgoing JSON.

## 🗄 Database Schema (SQLModel + Postgres)

### 1. Users Module Schema
* **User** Table: The core identity linked to Supabase Auth.
  * `id` (UUID, Primary Key): Exactly corresponds to the `auth.users` UUID generated by Supabase.
  * `username` (String, Unique)
  * `total_lifetime_steps`, `total_hexes_captured` (Int)
  * `current_streak`, `longest_streak` (Int)
  * `last_activity_date` (Date)
* **Friendship** Table: Tracks friend requests.
  * Composite Primary Key: `requester_id` + `addressee_id`.
  * `status`: "pending", "accepted", "blocked".

### 2. Map Module Schema
* **HexOwnership** Table: The "King of the Hill" engine.
  * `hex_id` (String, Primary Key): The H3 index string (e.g., "8a2a1072b59ffff"). Perfect for high-speed indexing.
  * `king_id` (UUID, Foreign Key): Refers to `User.id`.
  * `defense_score_steps` (Int): The number of steps the current King invested in capturing the hex. Contenders must beat this to steal.
  * `captured_at` (Datetime)
  * `times_stolen` (Int): Drives "Hotzone" mapping visualizers.

*(We specifically DO NOT track historical ownership logs in this table to ensure MapLibre viewport bounding box queries remain blazing fast).*

### 3. Runs (Capture Sync) Module Schema
* **RunSession** Table: Logs actual instances of users walking/running.
  * `id` (String, UUID)
  * `user_id` (UUID, Foreign Key)
  * `started_at` (Datetime)
* **CapturedHex** Table: Audit log mapping hexes physically captured during a specific run.
  * `run_id` (String, Foreign Key)
  * `hex_id` (String, Indexed)

*(Note: Data from runs immediately synchronizes & UPSERTs the `HexOwnership` table).*

### 4. Quests Module Schema
* **Quest** Table: Global definition of a server challenge.
  * `id` (UUID), `title`, `description`
  * `target_metric` (e.g., "steps", "hexes_captured")
  * `target_value` (Int), `reward_xp` (Int)
* **UserQuest** Table: Individual progress tracker.
  * Composite Primary Key: `user_id` + `quest_id`.
  * `current_progress` (Int), `is_completed` (Bool).

## 📡 API Contracts (Mobile App DTOs)

### Runs Payload (The Sync Engine)
When the Android mobile client stops a run (via `HexCaptureEngine`), it sends an EXACT payload that the API parses linearly:

```json
// POST /api/v1/runs/sync
{
  "total_session_steps": 1500,
  "hexes_to_steps": {
    "8a2a1072b59ffff": 400,
    "8a2a1072b59fffe": 1100
  }
}
```

The Service then replies with a gamified `RunSyncSummary`:
```json
{
  "hexes_defended": 1,
  "hexes_stolen": 1,
  "hexes_newly_captured": 0,
  "xp_earned": 500,
  "new_total_lifetime_steps": 35000
}
```

### Map Viewports (Zoom-Aware)
The map API (`GET /api/v1/map/viewport`) accepts bounding boxes and zoom levels from MapLibre.
* **Zoom >= 14 (Street Level):** The API executes bounding box exact SELECTs and returns `HexDetailResponse` (with `is_owned_by_me` boolean and `king_username`).
* **Zoom < 14 (City Level):** The API uses `h3_to_parent(hex_id, 6)` via DB raw SQL matching to build `HeatmapResponse` objects, returning aggregated zones outlining which player holds the most territory in a macro-grid.

### Users (Flattened)
The `UserProfileResponse` strips away graph data, returning simple top-level attributes, enabling the mobile UI to paint profiles instantly without chaining backend queries mentally.

## 🔐 Authentication Ecosystem (Deferred — Design Intent Only)

> **Status: NOT IMPLEMENTED.** Per SRS §4.2 authentication is postponed. The live
> backend uses a fixed development-user stub (`get_current_user` in
> `app/api/dependencies.py`); no request carries a real JWT and no
> `supabase.auth` verifier runs. The numbered flow below is intended future
> design, not current behavior.

1. **Supabase Client Flow:** Android registers/authenticates via Supabase directly.
2. **Postgres Sync Trigger:** Supabase creates the `user` table row natively using database triggers upon sign up.
3. **API Authorizer:** The Mobile app attaches the Bearer JWT to the headers. FastAPI (`dependencies.py`) takes that token and passes it to the `supabase-py` verifier (`supabase.auth.get_user()`) to decode the incoming `UUID`.
