# ADR 0005: M8.4 — Native Android Text-to-Speech for Live Coaching

Status: implemented 2026-09-06, real-device E2E verified (see "Real-device
verification"). Fifth slice of FitQuest SRS §15/§16 "Real-Time AI Coaching",
and the voice half of the SRS §15.3 MVP: "AI response text → Android TTS →
spoken coaching". Adds **native** speech (`android.speech.tts.TextToSpeech`)
for each genuinely **new** live `coaching_message` — with no cloud TTS, no API
keys, no paid or external TTS dependency, and **no backend change**. The M8.3B
push pipeline (PushCoach → WS → `CoachingWsClient` → `LiveCoachStore` →
Home CoachCard) is untouched; TTS observes the same store flow and reads the
same messages the Home card already shows.

    PushCoach (M8.3A, unchanged) -> CoachingSessionManager (M8.2, unchanged)
        {"type":"coaching_message","coach":CoachResponse}
            |
            v  ws://<BACKEND_BASE_URL>/api/v1/ws/coaching   (M8.3B, unchanged)
    OkHttpCoachingSocketFactory -> CoachingWsClient -> LiveCoachStore
            |                                              |
            |                       StateFlow<CoachResponse?>  (live slot)
            |                                              |
            |                       +----------------------+------------+
            |                       | M8.4 (this slice)                |
            |                       v                                 v
            |              HomeTab CoachCard               CoachingSpeechController
            |              "⚡ Live coaching"              (app-scoped Koin singleton,
            |              (unchanged rendering)            collects message.drop(1))
            |                                              |
            |                                              v
            |                                     CoachingSpeechGate
            |                                     (bounded in-memory dedupe:
            |                                      context_fingerprint + content)
            |                                              | Speak(text) | Silent
            |                                              v
            |                                     TtsSynthesizer seam
            |                                              | (real) AndroidTtsSynthesizer
            |                                              v
            |                                   android.speech.tts.TextToSpeech
            |                                   (native, application context)
            v
    (pull GET /api/v1/coach + CoachFetcher/CoachCache unchanged)

This slice explicitly does **not** do: cloud TTS, API keys, paid/external TTS
providers, any backend or API change, rewriting Home/Coach UI, personalising
the voice, or adding a settings surface. It also deliberately does **not**
create a second coaching pipeline — speech is triggered by the exact state
through which a live message already reaches the UI.

## Context & Problem Statement

By M8.3B the app receives a real, grounded coaching message the moment a run
commits, but only *displays* it. The spec for this slice:

- **Native only:** use `android.speech.tts.TextToSpeech`. No cloud TTS, no API
  keys, no paid/external TTS dependencies.
- **Reuse the existing flow:** inspect the Android coaching/WebSocket
  implementation first and integrate with it; identify the exact state/event
  through which a new `coaching_message` reaches the UI and reuse that state
  flow rather than building a parallel coaching pipeline.
- **New-message detection:** speak only genuinely NEW coaching messages — NOT
  on recomposition, Home↔Profile navigation, returning to Home, WS reconnect,
  or same-message-again. Use the existing `CoachResponse` identity/fingerprint
  plus a small in-memory dedupe key; never persist TTS history to the DB.
- **Speech behavior:** a fresh live message is spoken (prefer the coach message
  text over metadata); overlapping speech is avoided (a newer message replaces
  the older one); the backend-generated response is never altered for TTS.
- **Lifecycle/cleanup:** stop speaking when appropriate; release/shutdown the
  engine cleanly when the app-level owner is destroyed; no Activity/Context
  leaks; no uncontrolled TTS instances across launches/navigation.
- **Optional UI control:** only if an obvious lightweight settings location
  exists, add a Voice toggle — otherwise do NOT invent a settings system;
  default sensible; disabling must prevent speech without affecting coaching
  messages.
- **Tests + build + docs**, and real-device verification when practical.

## Decisions

### 1. Native `android.speech.tts`, app-scoped, bound to the application context

`AndroidTtsSynthesizer` wraps `TextToSpeech` directly (SDK 24+; minSdk 24 is
fine, `UtteranceProgressListener.onStop(interrupted)` exists since API 23). The
engine is constructed with the **application** context (Koin resolves it via
`androidContext()`), so it holds no Activity and cannot leak a screen across
navigation. It lives for the process: one instance per launch, never
re-initialised by recomposition or tab switches.

Init is asynchronous and some devices report ERROR before a later SUCCESS (the
engine retries its service binding), so the adapter is **race-safe**: an
`onInit` that fires synchronously *inside* the constructor and one that fires
later on a binder thread are both handled (`configured` guard + re-check after
the engine reference is assigned). `isReady` only becomes `true` after a
`SUCCESS`; a final ERROR leaves it false — the app is unaffected, nothing
speaks, nothing crashes. On success the engine prefers
`setLanguage(Locale.getDefault())`; `LANG_MISSING_DATA`/`LANG_NOT_SUPPORTED`
is logged and the engine falls back to an installed voice. `release()` is
idempotent, shuts the engine down and nulls the ready listener. Every framework
call is wrapped in `runCatching`, so a dead TTS service or missing voice can
never crash the WebSocket live-coaching path, run sync, tracking or the UI.

### 2. Speech trigger = the EXISTING live store flow (no parallel pipeline)

There is exactly one state through which a new message reaches the UI:
`CoachingWsClient` → `LiveCoachStore.publish` → `StateFlow<CoachResponse?>`
(`LiveCoachStore.message`), collected by `HomeTab` for the card. The
coordinator (`CoachingSpeechController`) is a Koin singleton on the process
`AppScope` that collects **that same flow** at app scope:

    liveCoachStore.message.drop(1).collect { onCoachingMessage(it) }

- `drop(1)` skips whatever the store already held at subscription, so a
  **retained** message from an earlier foreground is never re-read on app start,
  reconnect or re-entry.
- The collector lives in the process (`FitQuestApp` resolves and starts it
  once), deliberately NOT inside a composition — recomposition, tab navigation,
  Home → Profile → Home and returning to Home publish nothing and so can never
  retrigger speech. Speech is triggered by the push itself, which also means a
  fresh push is spoken even if the user is on another tab.
- Reconnect delivers no replay (push-only transport), and the gate (§3) plus
  `drop(1)` make even a hypothetical redelivery silent.

### 3. "Genuinely new" = gate on context_fingerprint + content (bounded, in-memory)

`CoachingSpeechGate` is a pure, thread-safe, **bounded in-memory** recent-set:

- A message is speakable only if `response.message` is non-blank.
- The dedupe key is `(context_fingerprint ?: "", normalizedText)`. A redelivered
  copy of the same message — a reconnect replay, a fan-out duplicate, a backend
  retry that regenerates identical text — has the same key and is `Silent`. A
  genuinely different message (new context and/or new content) is `Speak`. The
  capacity is a small ring (default 16), so memory stays fixed.
- **Nothing is persisted to the database.** On process death the set is gone,
  which is correct: a brand-new process has no reason to treat its first push as
  old news, and `LiveCoachStore` is empty at cold start anyway.

### 4. What is spoken: the coach message, TTS-lightly normalized

`speechText(response)` returns the message text (`CoachResponse.message`, the
AI coach copy) — not trigger metadata. The copy handed to the engine is
normalised for reading aloud: inline-code backticks and `**` markers removed,
markdown links reduced to their label (a URL read aloud is noise), the unicode
ellipsis becomes a full stop, and any newline/whitespace run becomes one space.
This normalisation is applied **only** to the TTS copy — the Home card
continues to render the backend message byte-for-byte (the backend-generated
response is never altered).

### 5. Replacement semantics: no overlap, newer message flushes the older

Every speak uses `QUEUE_FLUSH`, so a newer coaching message immediately
replaces an older one still being read (never queues behind it). If a fresh
message arrives while the engine is still binding, the coordinator keeps a
single **latest-wins** pending text and speaks it when the engine reports ready;
a second newer message while pending replaces the first. If the engine never
becomes ready, nothing is spoken and nothing crashes. Utterances carry a
`KEY_PARAM_UTTERANCE_ID` (`fq-coach-N`) and a `UtteranceProgressListener` logs
start/done/error/stop — used as the on-device evidence below.

### 6. Failure handling: never crash, never block

Every failure path is contained and logged under `CoachingTts`: construction
failure, init ERROR, unavailable/missing language, dead service, speak errors,
shutdown errors. TTS shares no state with the WS client, run sync,
reconciliation, `CoachCache` or tracking, so its liveness cannot affect them.
A device with no usable TTS voice silently runs with no coaching audio.

### 7. Lifecycle & cleanup

Because the synthesizer is app-scoped, speech intentionally continues across
tab navigation and (by default) across backgrounding — a run session's spoken
coaching is not cut the instant the user glances at another screen; the
utterance is allowed to finish. Speech is stopped when `enabled` is set false
(`stop()` + pending cleared), by `stopSpeaking()`, and on `release()`, which
also cancels the collector and shuts down the engine idempotently. `release()`
is the teardown path for the app-level owner; there are no Activity references
anywhere in the chain, so there is nothing to leak on navigation. MainActivity
does NOT connect/disconnect TTS with the WS (that is the deliberate difference
from the M8.3B socket lifecycle): TTS is process-scoped, not foreground-scoped.

### 8. No settings UI — a programmatic `enabled` seam only

An audit of the Android source found no settings surface at all (no
SharedPreferences, DataStore, or Switch anywhere). The spec forbids inventing a
settings system, so M8.4 adds none. `CoachingSpeechController.enabled`
defaults to `true` as the programmatic seam for a future toggle (and is proven
by tests to stop speech without affecting `LiveCoachStore` or the card).

### 9. Testability seam: `TtsSynthesizer`

`core/tts/TtsSynthesizer.kt` is the tiny interface the coordinator depends on
(`isReady`, `setOnReadyChanged`, `speak`, `stop`, `release`); the real adapter
is framework glue (android.speech.tts is not constructible in a JVM unit test,
exactly like the M8.3B socket). Tests drive a fake synthesizer on
`Dispatchers.Unconfined`, so a publish to the real `LiveCoachStore` resumes the
collector synchronously on the test thread — deterministic, no network, no
time-based waits, no `kotlinx-coroutines-test`.

## Files

Android main (`apps/app/fitquest/src/main/java/com/example/mobileapp/`):

- `core/tts/TtsSynthesizer.kt` — new: JVM-testable speech seam (contract:
  best-effort, never throws to the caller).
- `core/tts/AndroidTtsSynthesizer.kt` — new: real adapter over native
  `TextToSpeech` (application context, async race-safe init, ready-listener
  reports current value on registration, `QUEUE_FLUSH`/`QUEUE_ADD`, utterance
  ids `fq-coach-N`, `runCatching` everywhere).
- `core/tts/CoachingSpeechGate.kt` — new: pure bounded in-memory dedupe +
  TTS-friendly `speechText` normalization.
- `core/tts/CoachingSpeechController.kt` — new: app-scoped orchestrator
  collecting the EXISTING `LiveCoachStore.message.drop(1)`; latest-wins
  pending; `enabled` seam; `release()` teardown.
- `di/AppModule.kt` — new Koin singles (gate, `TtsSynthesizer`,
  `CoachingSpeechController`), all on the process scope.
- `FitQuestApp.kt` — resolves and `.start()`s the controller once at startup
  (inside a `runCatching`-style guard; the whole block is `try/catch` so voice
  coaching can never break app boot).

Tests (`apps/app/fitquest/src/test/java/com/example/mobileapp/core/tts/`):

- `CoachingSpeechGateTest.kt` — 8 tests: new message Speak; redelivered
  duplicate Silent (even as a different `generated_at` instance); different
  content Speak; identical content under a new fingerprint Speak; blank/null
  Silent; normalization for reading; bounded eviction; `decide` never throws on
  degenerate inputs.
- `CoachingSpeechControllerTest.kt` — 13 tests over a fake synthesizer + the
  real `LiveCoachStore`: new message spoken with `flush=true`; duplicate not
  re-spoken; newer/different message spoken; same wording + new fingerprint
  spoken; stale retained message before start never spoken; `start()` idempotent;
  messages before readiness → only the newest pending spoken when ready; late
  ready recovery; engine never ready → no speak, no crash, store intact; engine
  speak error swallowed then later messages spoken; blank never spoken; disable
  stops speech while messages still flow to the store + re-enable works; release
  stops observation + releases the engine.

## Real-device verification (PASS, 2026-09-06)

The rebuilt debug APK was installed on the physical Samsung device
(`RZ8R90661CF`) and driven end-to-end against the running dev backend
(`http://127.0.0.1:8000`, current main, WS route live). Logcat tags:
`CoachingWs` (M8.3B socket) and `CoachingTts` (M8.4 speech).

1. **Fresh run → real coaching_message → spoken.** App foreground → WS
   CONNECTING → CONNECTED. A fresh run sync (new `run_id`
   `5f50049a-6655-4118-b9cf-02016a6a0ff2`, 2,000 steps, no hexes) was POSTed;
   it committed credit (`already_processed: false`) and fired the
   `workout_completed` trigger → `PushCoach` → `coaching_message` over the
   socket. Logcat:
   `CoachingTts: speak queued id=fq-coach-1 flush=true chars=366 text="That run keeps your consistency strong—10 hexes in 7 days is"` then
   `CoachingTts: utterance started id=fq-coach-1` and later
   `CoachingTts: utterance done id=fq-coach-1` — the native engine began and
   finished reading the real message aloud.
2. **Navigate away/back + WS reconnect → NOT spoken again.** The app was sent
   to the background (activity stop → `CoachingWs: status=IDLE`), then
   relaunched (WS CONNECTING → CONNECTED again; Home recomposed with the
   retained live card). Logcat shows exactly one `speak queued` for the whole
   session (`fq-coach-1`) — the retained message was **not** re-read aloud
   (drop(1) + the gate).
3. **A second fresh coaching event → NEW message spoken.** After the push
   cooldown, a second fresh run sync (new `run_id`
   `e06d39d1-1183-455f-bc09-7114950d0a69`, 3,500 steps, no hexes) produced a
   second, different utterance: `CoachingTts: speak queued id=fq-coach-2
   flush=true chars=317 text="Nice momentum — 10 hexes captured in the past week
   and a run"` then `utterance started id=fq-coach-2`. A UI-hierarchy dump of the
   Home screen at that moment confirmed the **"⚡ Live coaching"** card body was
   the same message that was spoken ("Nice momentum — 10 hexes captured in the
   past week and a run in today is solid progress. …"). Screenshot evidence:
   `docs/docs/ui/evidence-m84/m84-tts-live-card.png` (+ `.txt` dump).

Scope note on the voice evidence: "spoken" is proven at the engine level
(`utterance started`/`done` are the framework's acknowledgements that speech
was synthesised and read out). Device media volume was not boosted and no human
ear/microphone confirmation was performed, so audibility at a given volume was
not asserted — the framework lifecycle is the evidence of speech.

The two dev-sandbox run syncs (2,000 + 3,500 steps, fresh `run_id`s, no hexes)
are test mutations against the dev user; no backend behavior or API was
changed, and no git operations were performed.

## What remains (M9 and later)

- Voice personalization (rate/pitch/voice choice) and an on/off setting once the
  app grows a real settings surface — `enabled` is already the seam.
- Backend-driven TTS or spoken notifications are explicitly out of scope: the
  SRS MVP is client-side native speech of the live coaching message.
- Revisit whether backgrounding should pause speech (a policy choice; the
  current app-scoped behavior lets a run-session message finish).
